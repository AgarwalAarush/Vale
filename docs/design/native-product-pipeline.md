## 2. Resolve native structure before styling

Build the approved one-panel Pearl structure in a real AppKit floating panel with a stable native editor. Start with Ready, disconnected/connected Ask and ordinary Answer. Keep the top-right anchor fixed as it changes size; no titlebar, traffic lights, persistent sidebar or second assistant workspace. Use system type, native symbols, native material, native menus and responder behavior. Retained history/settings/files/notes/Learn routes reveal on demand in the same panel. No web rewrite, hero, global kit installation or service rewrite.

The Ready editor is the input pill; expansion preserves its identity. In Answer the follow-up composer stays at the bottom. Disconnected users can draft/attach locally; Connect ChatGPT to send replaces unavailable Send. Connecting/cancel/retry remains adjacent. Browser return never automatically sends. Optional capabilities stay discoverable but subordinate; active voice/sharing always has an immediate stop.

Layout is content-led and bounded to the screen visible frame. Long questions/replies scroll; secondary routes may use a practical bounded expansion while retaining the same physical panel. The approved comp governs topology; normal-size text, safe placement and privacy govern translation details. Point dimensions are implementation choices, not HIG law. This host runs macOS15. Its matching Xcode26SDK can compile native glass, but an inherited SDKROOT originally pointed to an older CLTSDK. Build with the matching SDK explicitly; inspect the material fallback here and keep exact26optics unverified.

## 3. Implement with bounded ownership and appropriate checks

The coordinator owns shared build/runner, integration, tracker and acceptance. Delegate nonoverlapping files or reviews. Preserve editor identity, marked text, selection, undo, session/request ownership, files, restored drafts and every retained capability. Keep voice/screen consent explicit. Compile the candidate and finish required build preflight before freezing it for formal review; syntax parsing alone is insufficient. Independent source review may overlap runtime verification after compilation passes. Run meaningful integrated core/native checks; repeat only for changed inputs, failures or unresolved uncertainty. Profile actual stalls rather than adding empty performance ceremony.

Use Impeccable Operate for hierarchy and fresh critique; installed SwiftUI Pro for native state/accessibility/availability review with explicit macOS14 constraints; general Taste craft only, since its scope excludes complex product UI. Remove arbitrary design dials. Local SwiftUI Pro1.1 and remotely audited2.0.0 differ. Verify introduced APIs in the actual SDK. Factory organizes evidence; no skill certifies aesthetics.

## 4. Inspect the complete window and independently reject or accept

Establish available capture/input capability first. Current host exposes no native CUA surface. An isolated app-owned full-frame in-process raster can reveal titlebar/traffic-light/toolbar defects; it is neither compositor nor physical-input evidence. No obsolete CGWindowListCreateImage workaround, full-display fallback, TCC reset or unrelated-content capture. Content-only images cannot close chrome acceptance.

Record revision/build, generated state, logical frame, pixels/scale, appearance and method. Inspect every required image for correct state, full chrome and no blank/clipped regions. Keep private user screenshots out of public artifacts. Batch minimum/default/wide, light/dark and important states: disconnected/error, realistic conversation/history/long titles, files/notes/settings, loading/retry/Learn and active context/voice. Inspect combinations that stress changed structure. Builder gets one inspection batch, one combined fix batch and at most one confirmation batch; independent review is separate.

A fresh critic receives exact clean revision, owner rejection, references, complete images and literal evidence labels. Reject duplicate chrome, competing Connect/Send, oversized empty modules, missing capability routes, broken panel combinations, clipping or editor/data regressions. Repair material findings before decorative polish. Factory's four reviews target the same frozen source before repairs. The owner explicitly requested continued work after rounds8–10; the narrowly scoped continuation fixes the remaining proven toolbar ownership defect and confirms its affected routes. It does not reopen decorative polish or authorize an open-ended redesign.

## 5. Deliver only what evidence supports

Track implementation, visual quality, physical input/accessibility/hardware, genuine provider, signed package/feed, and installed/update/relaunch separately. Missing input/account capability keeps its acceptance open while independent work proceeds. Substantiate official authorization for the exact third-party ChatGPT route before calling it supported. Fixtures and familiar login branding do not establish support.

After native review, package the accepted immutable candidate with a new version/hashes, preserving updater trust and key custody. Never overwrite a published version. Release publication is already authorized. Inspect package, anonymously fetch public assets, and verify the actual configured update path. DMG validation does not establish target-laptop install/Gatekeeper/AppleSilicon/cleanup/relaunch. Preserve data; remove old copies only after replacement launch verification. Retain the prior stable feed until required stable gates pass.

Report useful result and exact remaining boundaries. Compilation, worker completion, test counts or a public preview never justify production-ready claims. Owner-reported failure reopens the relevant acceptance.
