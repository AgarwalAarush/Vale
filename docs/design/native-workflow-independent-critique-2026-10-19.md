## Challenge the proposed structure, not only its dimensions

An actual `NSToolbar` under the existing AppKit window owner is a strong experiment. `.unifiedCompact` is a candidate, not the answer by itself. There must be one coherent chrome band with ordinary traffic lights, drag behavior, readable current-conversation orientation, accessible title and narrowing behavior. A custom second toolbar beneath it fails even if its height is reduced.

The proposed 190–208-point rail, 24–28-point rows and 70–90-point composer are hypotheses. A narrower rail may truncate every useful chat title. Small fixed rows may clip larger text or force decorative metadata into unreadable type. Keep prose comfortably readable and remove wasted space first. Use real long titles and enough history to scan, not three tidy fixtures.

The geometry has a concrete unresolved conflict: a roughly 200-point rail plus 320-point inspector plus 48 points of reading gutters leaves about **472 points** inside a 1040-point window. That cannot simultaneously preserve a 640–700-point reading measure. A single 860-point breakpoint does not settle it. Choose rail/detail replacement from the remaining usable conversation width; test the actual combination, not each panel independently. A maximum prose measure is not a minimum that every window can satisfy.

I challenge the existing plan to center the editor on first launch and move it down after the first message. That creates a continuity and native-editor risk for little demonstrated benefit. Prefer a stable bottom composer across empty and populated states, with a brief nearby invitation and normal empty space above it. Keep the same mounted editor across navigation; do not recreate it merely to achieve alignment. If another position wins in a native comparison, prove the transition preserves focus, selection, marked text and draft ownership. Do not approve it from a still image alone.

## Endorsed first-run hierarchy

Use state-specific priorities rather than the same welcome composition with different labels:

| State | Primary task and presentation |
| --- | --- |
| Disconnected | Let the user write a local draft. Place one explicit **Connect ChatGPT to send** action at the composer, in place of unavailable Send. Explain the dependency once. Local attachments may remain available; optional capture/voice stay subordinate. |
| Connecting / failed | Keep progress, Cancel or Retry adjacent to that action. Preserve the draft and files across browser return. Do not automatically send a draft merely because connection succeeded. |
| Connected, empty | Focus the editor; Send becomes the clear message action. Use one short invitation rather than a generic large hero or setup block. |
| Restored conversation/draft | Restore the task directly, including relevant selection/scroll/draft state. Do not repeat onboarding. |
| Responding / failure | Put Stop or Retry beside the response it controls. Preserve the user's ability to read/select text and continue drafting. Never insert a completion into a different conversation. |

Keep the saved Web on/off choice explicit without suggesting search success. Group Talk/Conversation behind one understandable voice entry while preserving both modes; expose a clear persistent stop while active. Active sharing must identify the selected target and offer Stop sharing. Notes, files, Learn and timer need discoverable destinations, not permanent competing first-run modules. Standard duplicated access through menus/shortcuts is useful; a redundant empty history record is not.

## Concrete rejection criteria

Reject the next candidate if any of these remain:

- Blank titlebar plus a second application toolbar; clipped/overlapping traffic lights or controls; visual evidence that omits the chrome.
- Competing Connect and Send actions, “ready” messaging inconsistent with connection state, a giant initial editor/hero, or an empty selected history record with no user task behind it.
- Minimum/default width works only with empty fixtures; detail/history combinations hide the editor, force avoidable horizontal scrolling, or make the reading area unusable.
- Composer reparenting/navigation resets focus, marked text, selection, undo or drafts; switching chats permits stale response/context completion; restoring silently loses files or draft content.
- A retained capability is removed or buried beyond a recognizable route; optional screen/mic consent activates during ordinary typing; active capture/voice lacks an immediate stop.
- An independent critic reports unresolved high-priority hierarchy defects, or the coordinator closes those defects by citing test counts, palette compliance or its own authored DESIGN numbers.
- “Native verified,” “ChatGPT works,” “updates delivered,” or “installed on the laptop” is asserted with the wrong evidence class.

Evidence labels must remain literal: **in-process raster** establishes the rendered native hierarchy; **compositor capture** establishes pixels supplied by the window server for the captured window; **physical-input journey** establishes the actual exercised typing/clicking/focus flow; **live-service evidence** establishes genuine consent/inference/tool events for that account and route; **delivery evidence** establishes the downloaded package and update/install/relaunch that were actually exercised. None substitutes for another. No new compositor or physical-input evidence was produced by this review.
