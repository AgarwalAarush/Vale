# Signed automatic updates

Vale 1.3.0 and the 1.3.1 candidate use the embedded Sparkle 2.10.0 SDK for automatic checks, downloads, verification and installation. A valid configured build starts Sparkle at launch. Automatic checks and automatic download/install default on; Settings exposes each choice and Sparkle persists it. Launching Vale does not reset a saved preference. Turning off automatic checking leaves the manual **Check for Updates** action available.

Automatic downloads are verified and normally staged for installation when Vale quits. Vale does not force a conversation to close or add a login item or background daemon. Sparkle may need authorization or present its standard reminder/install UI. Checks run while Vale is open, on Sparkle's schedule; they are not a promise of an immediate daily background service.

The previously delivered Vale 1.2.3 build 6 has no feed/public key and cannot discover this configuration retroactively. It needs one manual installation of a configured bootstrap build. Source implementation, a locally configured candidate, a successful isolated SDK test, publication, and installation on the user's laptop remain separate delivery milestones. Production publication and the unavailable laptop's install/Gatekeeper behavior must be recorded by the coordinator with current evidence; this document alone does not establish either.

The [1.3.0 bootstrap release](https://github.com/AgarwalAarush/Vale/releases/tag/v1.3.0) is public. Anonymous HTTPS downloads of the signed feed, update ZIP and laptop DMG match the reviewed bytes. Both downloaded signatures verify against the bundled public key. A disposable copy of that downloaded Vale app completed an actual UpdateController/Sparkle production-feed check with “Vale is up to date,” preserving saved automatic choices across separate launches. The release’s `delivery-receipt.json` records this later delivery evidence; earlier preparation manifests retain their preparation-time flags. This check does not establish a full production old-to-new installation or laptop behavior.

## Trust policy

- The feed must use HTTPS without embedded credentials, whitespace or fragments, with a base64 Ed25519 public key that decodes to 32 bytes.
- The bundle requires `SURequireSignedFeed=true`, `SUVerifyUpdateBeforeExtraction=true`, and explicit `SUSignedFeedFailureExpirationInterval=0`. Zero prevents Sparkle's otherwise time-limited recovery from a persistently invalid feed signature. Missing or invalid configuration leaves the engine inactive.
- Primary, delta and full-archive fallback URLs must use the feed's same HTTPS host and port, without embedded credentials or fragments. The delegate rechecks the actual initial download request and clears a denied URL before connecting. Sparkle may follow later HTTP redirects, so verification of the exact archive before extraction remains required.
- The SDK verifies the signed feed and archive. Vale does not add an unchecked downloader or an unsigned fallback. It uses Sparkle's stored preferences directly rather than maintaining competing defaults.
- Native `--self-test` and `--integration-test` launches do not create the production updater. Explicit `UpdateController(info:automaticStart:false)` fixtures validate configuration without creating a backend, contacting a feed or mutating the main app's Sparkle preferences.

## Configuration and key custody

The intended stable GitHub feed uses a release asset URL such as `https://github.com/AgarwalAarush/Vale/releases/latest/download/appcast.xml`. Versioned archives use `https://github.com/AgarwalAarush/Vale/releases/download/TAG/Vale-VERSION-macOS-universal.zip`. Both initial URLs have the same host; combining a raw.githubusercontent.com feed with github.com archives fails the policy. Release assets must be anonymously accessible to the app. A signed-in developer CLI does not grant Sparkle access to a private repository, and tokens must not be embedded in the app or feed URL.

`scripts/configure-updates.py PATH_TO_INFO_PLIST` validates baked public metadata. Explicit `VALE_UPDATE_FEED_URL` and `VALE_UPDATE_PUBLIC_KEY` overrides embed public configuration, strict verification gates, and automatic defaults before app signing. It removes the old prohibition on automatic downloads. With no feed/key, it leaves the plist untouched; partial or insecure input fails before a write. These variables must never contain a private key.

The coordinator owns signing operations. A persistent authorized filesystem signing key may live in the **original repository's git common directory**, outside Factory source worktrees, under `codex-factory/private/` (0700 directory, 0600 user-owned key, no symlinks). Never track, package, print or place private bytes in arguments or environment. The update channel has a dedicated production seed in that protected private directory; only its derived public key is committed. It currently has one local custody copy and no verified external backup. Preserve it across repository cleanup and arrange an encrypted backup before relying on this channel long term. Production and disposable fixture keys are distinct.

Sparkle's tools accept a base64 raw 32-byte Ed25519 seed via `--ed-key-file ABSOLUTE_PATH` (legacy 96-byte key files are also supported). Always supply that flag for the selected filesystem custody; omission falls back to Keychain. `generate_keys` normally uses persistent Keychain storage and is not needed for the file-custody route. Only the derived public key belongs in the app.

## Release preparation and verification

1. Increment `CFBundleVersion` and assemble the configured universal app, preserving `local.lilt.companion`, legacy stores and valid nested Sparkle signatures. Verify the built bundle's actual metadata, architectures and strict code signature.
2. Create the Sparkle update archive containing only `Vale.app` with `ditto -c -k --sequesterRsrc --keepParent`. Keep the manual DMG/setup package separate. Prefer full archives initially; `generate_appcast --maximum-deltas 0` avoids delta complexity.
3. In a dedicated staging directory, sign the exact archive and feed with the authorized key. `generate_appcast --ed-key-file PATH` can generate/sign appcasts and notes; it caches extraction and may move old archives, so do not aim it at arbitrary source/download directories. `sign_update --ed-key-file PATH appcast.xml` signs an existing feed in place by appending a signature footer over preceding bytes. Any later XML or external-notes edit requires re-signing. Preserve old feed entries and their versioned archive URLs.
4. Verify signatures and extracted app identity/version/hash before publication. Test a real signed old-to-new update through the embedded SDK in a separate disposable bundle/data/defaults domain. Require actual download, verification, replacement, new executable launch and preservation of generated data. Tampered feed/archive tests must show a cryptographic SDK rejection and unchanged runnable old app; policy tests alone are insufficient.
5. A test-only loopback HTTP fixture can establish real SDK/ad-hoc signing behavior without system trust changes. It does not prove production HTTPS, GitHub redirects, notarization, Apple Silicon runtime or laptop installation. Keep production HTTPS/origin policy strict. Developer ID signing and notarization are recommended for public macOS distribution; valid EdDSA plus ad-hoc app signing can support a private isolated Sparkle test.
6. Prepare exact app/archive/appcast/notes/checksum artifacts for review. Publishing source or binaries requires the owner's explicit request. After approval, publish the reviewed bytes, fetch feed/archive anonymously over HTTPS, verify signatures and release identity, then check that source with the actual configured candidate in a disposable app/data/defaults domain. Record the live check separately from the real isolated SDK upgrade. A successful no-update cycle does not establish a live older-to-newer installation.

Focused checks: `scripts/check-update-config.py` covers public build metadata/defaults and mutation refusal. Core checks cover configuration, strict feed expiration, native-test isolation and archive origins. The native harness covers the app/Settings integration without contacting production. The coordinator records real SDK fixture and live published-feed outcomes separately.

Official references: [Sparkle setup and security](https://sparkle-project.org/documentation/), [preferences and automatic behavior](https://sparkle-project.org/documentation/customization/), [publishing signed updates](https://sparkle-project.org/documentation/publishing/).

`python3 scripts/verify-release-feed.py prepare dist/Vale.app` creates only a private temporary reidentified copy. `run RETURNED_ROOT` launches that copy twice, first saving automatic choices off and then verifying those choices survive relaunch, checking the real production HTTPS feed, and enabling the choices again. The app requires a nonce bundle identity with its isolated standard defaults domain and a private temporary marker before accepting this mode. Its receipts and native Settings PNGs contain generated data only. Real Sparkle writes preferences/caches in that nonce domain; no installed Vale or personal library is opened. The check may fail honestly before the approved feed is published.
